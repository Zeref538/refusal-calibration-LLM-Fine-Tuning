Case study — LLM fine-tuning & evaluation

Teaching a small model to say “I don’t know”
without making it say it too often

Small language models confabulate on questions outside their knowledge — confidently, fluently, wrong. The obvious fix (train it to refuse) creates a quieter failure: over-refusal, where the model declines things it actually knew. This project treats refusal as a calibration problem — measuring both error directions on the same held-out eval, across a tradeoff curve, rather than reporting a single flattering number.

The problem

Why "just train it to refuse" is a trap

Most published hallucination fixes report one number: the refusal or hallucination rate went down. They rarely report what happened to the questions the model could answer. A model that abstains on everything scores perfectly on hallucination and is useless in production. The honest deliverable is a curve, not a point.

Hallucination rate
↓ target
Confident wrong answers on unanswerable items
Over-refusal rate
↓ target
Abstentions on items the base model got right
Accuracy (answerable)
↑ target
Must not collapse while fixing the above

Method

Teach the model its own boundary, don't guess it

  1. Self-knowledge labeling

    Sample the base model k=16 times per question (8,000 TriviaQA questions) and check correctness against gold aliases, rather than assuming what the model "should" know. Questions it answers correctly above a threshold → answerable; near-zero → an unknown/defective abstain class. The model is taught its own boundary.

  2. A frozen, held-out eval

    800 items, stratified across four classes (answerable, unknown, defective, borderline), frozen before any training run touches it — enforced with a lock file so no later session can leak into it.

  3. 14 LoRA fine-tunes, one axis changed per run

    A tradeoff curve across the training mix (10/25/50/75/90% abstain examples), seed replicates to establish a noise floor, dosage (epochs) and capacity (rank/LR) ablations, and a 3B scale check — each isolating exactly one variable against a shared reference config.

  4. Both error directions, always paired

    Every run is scored for hallucination and over-refusal on the identical frozen eval, with bootstrap confidence intervals on the paired difference — so a 3-point gap isn't reported as if it were an 18-point one.

Engineering notes

The parts that weren't the model

Most of the real effort was making the pipeline survive Kaggle's constraints, not the fine-tuning itself:

  • Every stage (probe, build, train, generate, score) is resumable — a killed 9-hour session picks back up mid-arm instead of restarting.
  • The eval is frozen and lock-file enforced, so no later training run can accidentally leak into the numbers being reported on.
  • Every rate is reported with a bootstrap CI on the paired difference, so a 3-point gap and an 18-point gap are never conflated.
  • One script per pipeline stage, one YAML config per run — no per-run copy-pasted notebooks to drift out of sync.
